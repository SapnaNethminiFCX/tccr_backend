# TCCR Backend — System Specification

## Architecture and technology

The platform is built as a single modular monolith: one Node.js and TypeScript service running on Express, internally organised into domain modules (auth, users, courses, enrollment, progress, cells, reports, notifications, audit) that call one another in-process rather than over the network. Authentication is handled by Supabase Auth, the relational data lives in PostgreSQL hosted on Supabase, and the data access layer uses Drizzle ORM with drizzle-kit migrations. Uploaded images and PDFs are kept in Supabase Storage. All public routes are versioned under `/api/v1`, and every response follows a consistent envelope so the frontend can rely on a single contract.

The guiding design principle is that roles own tasks, not the other way around. The specification is organised by role, and each role lists every task it can perform; when two roles share a task, that task appears under both roles rather than being collapsed into a shared bucket. A user holds an additive set of roles, so the same person can be a member, a student, and a leader at once. The `member` role is the permanent base every account keeps; promotions add roles on top of it and demotions strip the elevated role while leaving `member` intact.

## Authentication

Both registration and login are performed client-side through the Supabase SDK. A registered user signs in with their email and password, and the SDK exchanges those credentials with Supabase for a short-lived JWT access token and a refresh token. In addition to email-and-password sign-in, users can log in with Google or Apple through Supabase's federated OAuth providers; the SDK completes the provider handshake and returns the same kind of Supabase session, so the rest of the backend treats a federated session identically to a password session. The client sends the access token as a Bearer token on every request, and the backend's authentication middleware verifies the JWT, extracts the user id, email, and email-verification status, then loads the user's roles and account status from the database to build the request principal. To protect against brute-force attempts, the backend tracks failed sign-ins: after a configured number of failures within a time window the account is temporarily locked and further attempts are refused until the window clears, and successful sign-ins reset the counter. Email verification is handled by Supabase: a confirmation email is sent on sign-up, and unverified users are rejected until they confirm, while federated Google and Apple sign-ins are treated as already verified. Password resets are issued by Supabase as well, so the backend never stores or handles raw passwords. When an administrator, G12 leader, or super admin creates a user directly, the account is provisioned through the Supabase Admin API with a temporary password, and a credentials or invitation email is sent so the new user can sign in and set their own password. The backend enforces an absolute session lifetime and distinguishes an expired access token (which the client silently refreshes and retries) from a revoked or expired session (which forces a clean logout). Authorization is evaluated per task against the caller's full set of roles, with super admin inheriting admin, and master inheriting G12 and the roles beneath it.

## Email and notifications

Email is delivered through two channels. The first channel is Supabase Auth, which owns every authentication-related email: the sign-up verification email, the password-reset email, the email-change confirmation, and the invitation email used when an account is created on a user's behalf. Supabase generates and sends these from its built-in templates, and to make them branded and reliable the project points Supabase at a configured SMTP sender rather than relying on its default low-volume mailer. Email verification therefore works entirely through this channel — Supabase emails the confirmation link or code on sign-up, marks the address verified when the user acts on it, and the backend's authentication gate refuses unverified accounts until that happens.

The second channel is the application's own transactional email, used for everything that is not an authentication event. The application sends an email in each of the following situations: when a student role request is approved or rejected, with the approval or rejection note included; when a course enrollment is approved or rejected; when an administrator, G12 leader, or super admin creates a new user directly with a role such as leader or G12, in which case the email carries the temporary password and login link so the new user can sign in and set their own password; and when a member is promoted to a new role or demoted from one, notifying the user that their access has changed. Together with these, the application also sends cell-report-filed notifications and cell ownership-transfer notices. All of these are sent by a single email service inside the monolith that talks to a transactional email provider over SMTP or its API; the same service renders the message templates and is the only component that sends mail, so every application email flows through one place. For completeness, the authentication channel above covers the remaining cases — the email-verification message on sign-up and the password-reset email — which are issued by Supabase rather than this service. Alongside email, in-app notifications are written to the database and read by the user from their notifications feed. To guarantee that no notification or email is lost, the intent to notify is recorded in the database within the same transaction as the action that triggered it and is then picked up and dispatched by an in-process background job runner, which retries on transient failures so a momentary provider outage does not drop a message.

## Member

Every newly registered user is a member and is taken to the member dashboard. From there a member may submit exactly one kind of self-service role request: a request to become a student. Members cannot request to become a leader, a G12 leader, or a master; those roles are only ever assigned by other people. Once submitted, the student role request sits in a pending state and the member can see that pending status on their dashboard; the request remains pending until an administrator or super admin reviews it, and only when it is approved does the member gain the student role and become a member and student combined, while a rejection leaves the member as a member and frees them to request again. A member can view their own in-app notifications, where they receive updates such as the outcome of their role request and other system messages, and can mark them as read. A member can also edit their own profile — phone number, address, date of birth, gender, first and last name, display name, preferred language, password, and profile photo — though the email address is shown read-only and cannot be changed.

## Student

A student can browse the published courses and request to enroll in any of them, which places the enrollment in a pending state. Once an administrator or super admin approves the enrollment, the student gains access to that course's content, navigating from semesters into subjects and then into lessons, and can download lesson attachments through enrollment-gated, time-limited links. The student always sees the course through the lens of the batch they were enrolled into: each semester carries the state derived from that batch's schedule — unscheduled, upcoming, open, or closed — so semesters become available to the student according to their own cohort's open and end dates rather than on fixed global dates, and a semester with no scheduled dates for their batch appears as unscheduled. The student's progress is tracked: marking a lesson complete is idempotent and automatically rolls up into subject completion once every lesson in a subject is finished, video positions are saved and resumed, and overall course progress is reported both by subject and by lesson. Importantly, leaders and G12 leaders who wish to take Bible School courses obtain the student role through this same request-and-approval path, so studying is always done as a student regardless of any other roles the person holds.

## Admin

An administrator manages the full course lifecycle. They create and edit courses and add semesters, batches, subjects, lessons, and attachments, and they publish, unpublish, archive, restore, and delete courses. Batches are intake cohorts that sit under a course and group students who enroll together; each batch moves through a draft, open, and closed lifecycle and defines an enrollment window with an intake start and end and an optional capacity, and a batch only accepts enrollments while it is open and the current time falls inside that window. An administrator can open and close batches to control when that enrollment window is active. Crucially, scheduling is per batch and per semester: rather than a course's semesters opening on fixed global dates, each batch carries its own open and end date for every semester in the course, so the same semester can run on different dates for different cohorts. An administrator can set all of a batch's semester dates at once or adjust a single semester's dates for a batch, and from these dates each semester's state for an enrolled student is derived as unscheduled, upcoming, open, or closed; a semester with no date record for the student's batch is treated as unscheduled. A student therefore sees a course through the lens of their own batch, with semesters becoming available according to that batch's schedule. For student role requests, an administrator can view, approve, or reject them, attaching an optional welcome or rejection note, and the requester may be a plain member or someone who also holds leader, G12, or master roles and simply wants student access for courses. For enrollments, an administrator reviews pending requests and approves or rejects them, optionally inspecting the student's profile first though doing so is not required. In user management, an administrator can view all users in the system, open any user's profile, promote a member to leader or G12 leader, demote a promoted leader or G12 leader back to member, and suspend, reactivate, or delete users. For cell groups, an administrator does not create cells but manages them: from the manage-cells area they can transfer cell ownership from one leader to another and from one G12 leader to another, transfer multiple cells to a single person in bulk, and delete cells. After a transfer leaves a leader or G12 leader with no cells remaining under them, the administrator can then demote that person to member; a leader or G12 leader may be demoted to member only once they have no cells left. An administrator can also create a new user directly by supplying a first name, last name, email, and temporary password and selecting a role of leader or G12 leader, after which the new account becomes a member combined with that role and receives a credentials email. An administrator can view the system activity logs, an append-only record of significant actions across the platform — such as registrations, role-request and enrollment decisions, promotions and demotions, suspensions and deletions, and cell ownership transfers — each entry capturing who performed the action, what was affected, and when, so the history can be reviewed and filtered. Finally, an administrator can view the dashboard data.

## Super Admin

A super admin can do everything an administrator can, and additionally manages administrators and the master role. They add administrators by sending an email invitation to log into the system, and they can suspend, reactivate, and delete existing administrators. They can assign or invite a single master for the entire platform, subject to a strict singleton rule: only one active master may exist at any time, and any attempt to promote an existing G12 user or invite a new user as master performs a concurrency-safe check and is rejected if a master is already active. A super admin can view the current master, and can suspend, reactivate, or delete the master like any other user. When creating users directly, a super admin may assign a role of leader, G12 leader, or master, with the master option always governed by the singleton rule. A super admin can also grant an existing G12 user organisation-wide, master-level report and analytics visibility without actually promoting them to master: the user's role remains G12, but a report-access flag (optionally with an expiry) lets them call the report endpoints with the master scope and see org-wide data, while still being unable to file or void reports, never appearing in the master lookup, and remaining blocked from every other master-only feature.

## Leader

A leader can create cells. When creating a cell the leader selects a Cell Name, an Area, and a Cell Type from Care, G12, Children, and Outreach, searches for and selects a G12 leader as the cell's supervisor using a search bar, and submits; the created date is recorded automatically. A leader can add only members to a cell, not other leaders. At creation time the leader can already add members, and can also add unregistered people who do not have a system account by entering their name and optional phone number directly. An added registered member is a user holding the member role, and such a member may belong to only one cell, so the member search should surface only members who are not already in a cell. From the Cells tab the leader can view all the cell groups in the system but can only edit and manage the cells they own. A cell can be edited at any time — there is no time limit on editing the cell itself — and while editing an owned cell the leader can add or remove members and add unregistered people, just as during creation. The only time-limited action is the cell report: a report that has already been filed can be edited only by the person who submitted it and only within twenty-four hours of submission. When filing a cell report the leader can also add unregistered people as attendees, and when a cell had no meeting the report does not require a location and that field may be left empty. Other cells in the system are visible to the leader only in appearance and cannot be viewed in detail or edited. A leader may also submit a request to the Bible School and enroll in its available courses as a student.

## G12 Leader

A G12 leader can create cells by selecting a Cell Name, an Area, and a Cell Type from Care, G12, Children, and Outreach, with the created date recorded automatically; because the G12 leader is themselves the supervisor, no supervisor field is shown. Unlike a leader, who can add only members, a G12 leader can add both members and leaders to their cells, and at creation time can also add unregistered people who do not have a system account by entering their name and optional phone number directly. The cell-membership rules differ by role: a member, or a member who is also a student, can belong to only one cell, while a leader may belong to more than one cell. From the Cells tab the G12 leader can see every cell group in the system, but their access is view-only for any cell that is not their own: they can open and inspect all cells for visibility, while they can edit and manage only the cells they own. A cell can be edited at any time — there is no time limit on editing the cell itself — and while editing an owned cell the G12 leader can add or remove members and leaders and add unregistered people, just as during creation. The only time-limited action is the cell report: a filed report can be edited only by its author and only within twenty-four hours of submission. When filing a cell report the G12 leader can also add unregistered people as attendees, and when a cell had no meeting the report does not require a location. The cells under their supervision — those in which leaders selected them as the supervisor — are likewise view-only and cannot be edited.

A G12 leader manages their network. They can view the leaders in their network, promote members to leader or G12 leader, promote leaders to G12, and demote promoted leaders or G12 leaders back to member. They can invite new users by providing a first name, last name, email, and temporary password and assigning a role of leader or G12 leader, which sends an email with login credentials. A distinctive capability of the G12 leader is generating a summary report of cell groups, filtered by a custom date range such as weekly or monthly by choosing a start and end date; when generating the report the G12 leader can select specific leaders under them to view the cell reports managed by those leaders, and can select the precise cells to include. The scope of this report is the G12 leader's own network: their own cells, the leaders beneath them, those leaders' cells, and all of the reports, attendance, and details within. A G12 leader may also request the Bible School and enroll in its courses as a student.

## Master

The master holds all the privileges of a G12 leader — a master is also a G12 — but with far broader visibility and reach. As a G12, the master can do everything a G12 leader does: create cells with a name, area, and cell type (without a supervisor field, since the master is themselves a supervisor); add members to their cells under the one-cell-per-member rule and add leaders, who may belong to more than one cell; view all cells, edit and manage the cells they own, and fill out cell reports subject to the same rule that a filed report may be edited only by its author within twenty-four hours and may omit a location when there was no meeting; view, but not edit, the cells under their supervision; manage their network by promoting members to leader or G12, promoting leaders to G12, and demoting promoted leaders or G12 leaders back to member; invite new users as leader or G12 with a temporary password and credentials email; generate cell-group summary reports filtered by a custom date range with selected leaders and cells; and request the Bible School and enroll in its courses as a student.

Beyond all of that, the master has cross-organisation reach. The master has organisation-wide visibility into all the data in the system, including every cell, every G12 leader and leader, every cell report, attendance, and all cell-related data across the whole platform. The master can view, file, and void cell reports platform-wide, access all analytics including the full G12 summary report at organisation scope, and promote members to leader or G12 anywhere in the organisation rather than only within a single network. Only one active master may exist at any time, enforced by the singleton rule, and the master accesses organisation-wide reports using the master scope.

## Reports and analytics

Reporting visibility depends on scope. A master, and any G12 leader granted master-level report access by a super admin, sees organisation-wide data: all cells, all G12 leaders and leaders, all cell reports, attendance, and every cell detail. This report-access grant can be given only to a G12 leader and only by a super admin — no other role can be granted it and no other role can grant it. A G12 leader who has not been granted it sees only their own network: their cells, the leaders under them, those leaders' cells, and the associated reports, attendance, and details. Reports are filtered by a custom date range using a start and end date, and the requester can narrow results to selected leaders and selected cells, with the data aggregated on demand for display in the executive reports section. The report endpoints take a role parameter that acts as the access gate rather than changing the data shape: a value of `g12` returns own-network scope and is available to any G12 leader, while a value of `master` returns organisation-wide scope and is permitted only when the caller is the master or holds the active report-access grant. Crucially, when a super admin grants a G12 leader the ability to view reports as a master, the G12 leader's role does not change — they simply call the report endpoint with the master scope to see all the data, while remaining a G12 leader in every other respect.

## Profiles

Every user can edit their own profile, including phone number, address, date of birth, gender, first and last name, display name, preferred language, password, and profile photo. The email address is displayed but cannot be changed. Registration requires only a first name, last name, and email; the first and last name are merged into a single display name when stored, and the display name is what is returned when user details are fetched.

## Database structure

The data model is relational and centred on a `profiles` table keyed by the Supabase auth user id, holding name, contact, demographic, language, photo, account status, and report-access fields. Roles are stored in a `user_roles` table so a user can hold several roles at once, with a partial unique index enforcing that only one active master can exist. The course domain is modelled as `courses`, `semesters`, `subjects`, `lessons`, and `attachments`, together with `batches` and a `batch_semesters` table that carries per-batch, per-semester scheduling. Enrollment and access requests are held in `role_requests`, whose requested role is constrained to student, and in `enrollments`, which tracks the pending, approved, rejected, and withdrawn states. Learning progress is captured in `subject_progress`, `lesson_progress`, and `video_progress`, each unique per student and item. The cell domain comprises `cell_groups` with a cell type, state, owning leader, and optional G12 supervisor; `cell_members`, which distinguishes registered members from external entries and uses a partial unique constraint so that an ordinary member belongs to only one cell while leaders are exempt and may join several; `cell_join_requests`; and `cell_reports`, which allows a null location for meetings that did not occur, enforces idempotency through a client-supplied request key, and is governed by the twenty-four-hour edit window in the service layer. Cross-cutting concerns are served by a `notifications` table, an append-only `audit_log`, and an outbox or job table that drives reliable background delivery of emails and notifications.

## API responses

Every endpoint returns a predictable shape. A request that reads or creates a single resource returns that object directly, with a 201 status on creation and 200 on a read or update, while an action that produces no resource returns a 200 with a short message, such as confirming an approval or a logout. List endpoints return an object containing the items, a pagination cursor or page marker, and a total count. A successful deletion returns 204 with no body. Errors always return an object containing an error code and human-readable message together with a request id at the root for log correlation, so the frontend can branch on a stable code — for example a conflict when assigning a second master, a validation error on an invalid report scope, or an edit-window-expired error when a cell report is changed after twenty-four hours.
